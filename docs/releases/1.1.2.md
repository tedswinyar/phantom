# 1.1.2 highlights

**Reclaim plans now hold back the paths a registered tool launches from.**
On 2026-09-16 a gate run moved `~/Code/vigil/rust/target` — gitignored,
rebuildable, correctly rated `safe` — and took the vigil MCP server with it,
because `~/.claude.json` registered that server's command from
`…/target/release/vigil-mcp`; every new session failed to start it until a
`cargo build --release`. Phantom was right that the bytes were reclaimable
and wrong that reclaiming them was free. `plan_reclaim` (and `phantom plan`,
and the app) now reads the user's registrations at plan time — MCP servers
in `~/.claude.json` (user level, per project, and each project's
`.mcp.json`), hook commands in `~/.claude/settings.json`,
`Program`/`ProgramArguments` in `~/Library/LaunchAgents/*.plist`, and the
symlink targets in `~/bin` and `~/.local/bin` — and holds back any plan path
that is, or contains, one of them. The item keeps its other paths and its
`why` names the held binary and the registration (`… is the launch path for
MCP server "vigil" (~/.claude.json)`); a group with nothing left is review at
plan time and counts in `skipped.review`. Files only, nothing executed. The
script header and the bundled reclaim skill now say which four sources
Phantom checked, so a runner greps only for registrations kept elsewhere.

**`phantom worktrees`: the swarm-sprawl report.** Agent swarms create linked
git worktrees and never remove them — 219 on the developer's Mac on
2026-09-27, 80 of them merged and still holding 37 GB, with `node_modules`
spread over ~45 copies too small to reach any group's `topPaths`. The new
CLI command folds a scan's project roots into the worktrees whose `.git`
file names another repository's `.git/worktrees/<name>`, asks git
(read-only, fixed path, scrubbed environment, 20 s bound, in the CLI's own
process — the API never runs git) which are merged into their default branch
— by ancestry or, for rebased merges, by `git cherry` — and clean, and
prints them per repository with the build output inside each, plus the ones
held back and why. The build directories inside are plan paths already; the
worktree itself is review, and the report names the actor (`git worktree
remove`, or a reaper such as wt-reap) because Phantom never deletes source.
On the developer's home scan it found 32 finished worktrees holding 3.6 GB,
2.8 GB of it six worktrees of one project at ~565 MB of `node_modules` each.
The API, MCP and app surfaces follow in a later release.

**The Homebrew cask is part of every release.** There is no separate tap
repository: `brew tap tedswinyar/phantom https://github.com/tedswinyar/phantom`,
`brew trust tedswinyar/phantom` (Homebrew 7 refuses casks from an untrusted
tap — the 1.1.1 install text was missing this line), `brew install --cask
phantom`. The 1.1.1 cask was committed to the public repository by hand and
the next recut would have dropped it; from 1.1.2 `release.sh` renders
`Casks/phantom.rb` from the notarized DMG's digest and commits it before
tagging, so the tag carries its own cask. The rendered cask interpolates the
version in its URL (clearing the `brew audit --strict` finding on 1.1.1),
declares `depends_on macos: :sonoma` in the form Homebrew no longer warns
about, and `--zap` now also removes `~/Library/HTTPStorages/com.tedswinyar.phantom`,
the one directory the 1.1.1 zap left behind. Proven on a fresh macOS VM that
had never seen Phantom.

**Upgrading.** No schema change and no wire change: a 1.1.1 database opens as
it is, every API response, MCP tool and CLI output keeps its 1.1.1 shape, and
the plugin manifests move to 1.1.2 so marketplace users pick up the revised
reclaim skill. The installed app updates through Sparkle (Phantom ▸ Check for
Updates…) or `brew upgrade --cask phantom` once the public repository is
recut. `phantom worktrees` needs `git` at `/usr/bin`, `/opt/homebrew/bin` or
`/usr/local/bin` and exits with "not found" otherwise; nothing else in
Phantom depends on it.
