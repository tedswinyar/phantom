# Build & release pipeline

How `scripts/build-dmg.sh` produces a signed, notarized `.dmg` — with
particular attention to notarization credential management, which is the
part that bites.

## Entry points

```bash
./scripts/build-app.sh                # .app bundle only (ad-hoc unless configured)
./scripts/build-dmg.sh                # full: build → sign → notarize+staple .app → DMG → notarize+staple DMG
./scripts/build-dmg.sh dmg            # DMG + notarize only; reuses last .app
SKIP_NOTARIZE=1 ./scripts/build-dmg.sh   # signed-but-unnotarized DMG
./scripts/release.sh <version>        # alignment gates → verify → DMG → notes → tag
./scripts/publish-release.sh <version> # EdDSA-signed appcast + GitHub Release on the PUBLIC repo
./scripts/recut-public.sh <version>   # rebuild the public repo (one squashed commit) — never hand-push it
./scripts/public-sweep.sh [<ref>]     # would <ref> (default HEAD) survive the public cut? same list + sweep as recut
./scripts/publish.sh                  # deploy website + artifacts (stub until configured)
```

The public sweep (`scripts/lib/public-sweep.sh`: the exclusion list plus the
personal/employer identifier greps) runs in three places from one definition:
`verify.sh`'s scripts suite on every push, the Release job before anything is
signed, and `recut-public.sh` last. The 1.1.0 cut taught why: the sweep ran
only in the recut, after the release was live, and found two personal paths in
test files (phantom-mj7). `recut-public.sh` is re-runnable: when the public
release already exists it re-points the tag and refreshes the notes; the
assets are never re-uploaded.

The release train is `release.sh` → `publish-release.sh`; both refuse to run
from anywhere but the private working repo (see "Sparkle update channel").

**Two tickets, not one (v1.1.0+, phantom-ojj.1).** The `.app` is zipped,
notarized and stapled BEFORE it is copied into the DMG, then the DMG is
notarized and stapled as before. v1.0.0 stapled only the DMG: the installed
app passed Gatekeeper via an online lookup, which an offline Mac — or a
Sparkle-installed update, which never sees the DMG — cannot do.
`publish-release.sh` mounts the DMG and refuses to publish unless
`stapler validate` passes on the app inside as well. `build-dmg.sh dmg`
skips the app step when the bundle already carries a ticket.

## Distribution artifacts (v1.1.0+, phantom-mkn.18)

`publish-release.sh` uploads the DMG, the signed appcast AND
`phantom-mcp-<version>.mcpb` (the MCPB bundle for Claude Desktop: the
`phantom-mcp` binary plus a `manifest.json`, built by
`scripts/lib/distribution.sh::build_mcpb`), and writes two files to `dist/`:

| File | What it is | After publish |
|---|---|---|
| `dist/phantom.rb` | Homebrew cask: `app` + `binary` stanzas for `phantom` and `phantom-mcp`, completions and the man page from `Contents/Resources/{completions,man}` (generated by `build-app.sh` from the shipped binary) | nothing — see "The public repo is the tap" below; `recut-public.sh` ships it as `Casks/phantom.rb`. |
| `dist/server.json` | MCP Registry entry `io.github.tedswinyar/phantom`, `registryType: mcpb` pointing at the `.mcpb` asset with its sha256 | **human:** `mcp-publisher login github` (once), then `mcp-publisher publish dist/server.json`. The registry is in preview. |
| `dist/phantom-mcp-<v>.mcpb` | already uploaded; unsigned | optional: `npx @anthropic-ai/mcpb sign` with the Developer ID, then re-upload |

### The public repo is the tap

There is no `tedswinyar/homebrew-tap` (Ted, 2026-09-27): Homebrew taps any
git repository, and the public `tedswinyar/phantom` carries `Casks/phantom.rb`.
Users:

```bash
brew tap tedswinyar/phantom https://github.com/tedswinyar/phantom
brew trust tedswinyar/phantom        # Homebrew 7 refuses to load casks from an untrusted tap
brew install --cask phantom          # or, once tapped: tedswinyar/phantom/phantom
```

The cask has to survive the recut, which rebuilds the public repo from
`git archive <tag>` — a cask that lived only in `dist/` (1.1.1's was
hand-committed to the public repo) would have vanished at the next cut. So:

- `release.sh` renders `Casks/phantom.rb` from the notarized DMG's digest and
  the public asset URL and commits it with the notes/SBOM **before tagging**,
  so the tag itself carries the cask for the version it ships. The source
  tree's `Casks/phantom.rb` is therefore always the last release's cask.
- `recut-public.sh` puts the cask in the export before the sweep, preferring
  `dist/phantom.rb` when it declares the version being cut, else the tag's
  own, else (a re-run without `dist/` of a tag older than this mechanism)
  one rendered from the published DMG — and **dies** if the export still has
  no `Casks/phantom.rb` declaring that version (`export_cask_ok`).
- `scripts/tests/test-distribution.sh` pins the refusal (an export without
  the cask, or with the previous version's, fails) and that the tree's cask
  is tracked; `test-release-dry-run.sh` pins that `release.sh` renders it
  with the DMG's sha256 and stages it in the release commit.

Proven on 2026-09-27 against the public repo: `brew tap`, `brew audit --cask
--online tedswinyar/phantom/phantom` and `brew fetch --cask` (digest check)
all pass; see the bead `phantom-cnr.8`.

## Identity lives in release.conf, nowhere else

`scripts/release.conf` (gitignored; `release.conf.example` documents it)
carries `SIGNING_IDENTITY`, the notarization credential, and deploy targets.
Without it, everything still works: ad-hoc signing, notarization skipped, DMG
usable locally. This is deliberate — a fresh clone must produce a runnable
build with zero Apple credentials. `PHANTOM_RELEASE_CONF` names a file
elsewhere; the build server keeps its config outside the checkout.

## Releases are cut on the build server

Since 2026-09-16 every release runs on the self-hosted runner described in
[docs/build-server.md](build-server.md): push `release/X.Y.Z` and the runner
runs `release.sh`, publishes, and recuts the public repository. Running the
scripts by hand on a developer Mac still works and is how the pipeline is
debugged, but it is not how anything ships. Three consequences for this
document:

- **Notarization on the build server uses an App Store Connect API key**
  (`NOTARY_KEY_PATH`/`NOTARY_KEY_ID`/`NOTARY_ISSUER_ID`), because a headless
  job cannot open the data-protection keychain the profile lives in. The
  profile shape below remains for interactive machines. `scripts/lib/notary.sh`
  decides which is in use; a half-set key is a hard error, never a silent
  fall-through (`scripts/tests/test-notary.sh`).
- **Signing goes through a named keychain** (`SIGNING_KEYCHAIN`) that the job
  unlocks from a 0600 password file, and the Sparkle appcast is signed from a
  key **file** (`SPARKLE_PRIVATE_KEY_FILE`, `generate_appcast --ed-key-file`)
  rather than the login Keychain.
- **The DMG from the runner is unstyled** (`SKIP_DMG_STYLE=1`): Finder
  scripting needs a GUI session the build user never has.

## Notarization credentials — why this is fragile

`xcrun notarytool` stores credentials in the **data-protection keychain**,
not the legacy login keychain. Consequences (inherited knowledge, paid for
repeatedly upstream):

1. `security find-generic-password` cannot see the item. The canonical
   "is it there?" check is
   `xcrun notarytool history --keychain-profile phantom-notarize`.
2. The profile can become inaccessible to CLI tools after wake-from-sleep, a
   Touch ID timeout in a non-interactive shell, or iCloud keychain events —
   failing with `No Keychain password item found for profile: …`.

What the script does about it:

- **Pre-flight, fail fast**: the history check runs BEFORE the multi-minute
  build.
- **Self-healing**: if the pre-flight fails and `APPLE_ID`,
  `APPLE_TEAM_ID`, `APPLE_APP_SPECIFIC_PASSWORD` are exported, the profile
  is re-provisioned via `store-credentials --no-validate` and the build
  proceeds.
- **Precise failure messaging**: mid-build failures are classified —
  credential-disappeared (re-run; pre-flight heals), service rejection
  (inspect `notarytool log <id>`), transient (retry `build-dmg.sh dmg`).
  A signed-but-unnotarized DMG is always left on disk so a later retry
  can staple without rebuilding.

## One-time setup on a new machine

```bash
xcrun notarytool store-credentials phantom-notarize \
    --apple-id <apple-id> --team-id <team-id>
xcrun notarytool history --keychain-profile phantom-notarize   # verify
cp scripts/release.conf.example scripts/release.conf              # fill in
```

## Common failure modes

| Symptom | Likely cause | Recovery |
|---|---|---|
| `No Keychain password item found` at submit | data-protection keychain locked | run any `notarytool` command interactively, re-run build; or export the self-heal env vars |
| `status: Invalid` from notary | bundle violates hardened-runtime rules | `xcrun notarytool log <id> --keychain-profile phantom-notarize` |
| DMG works locally, warns on other Macs | not notarized (SKIP_NOTARIZE or no profile) | check `xcrun stapler validate dist/…dmg`; re-run `./scripts/build-dmg.sh dmg` with credentials |
| Update check from a terminal-launched app "finds nothing" | Sparkle 2 defers a scheduled-check alert while the app is not frontmost; `SULastCheckTime` still advances | click into the app, or Phantom ▸ Check for Updates… (user-initiated checks always show a result) |
| `stapler validate` fails on the .app pulled out of the DMG | only the DMG is stapled (phantom-ojj.1) | Gatekeeper still accepts via online notary lookup; offline first launch may block — staple the .app before packaging |
| Release blocked: versions diverge | Version.swift ≠ OPE VERSION ≠ release arg | bump them deliberately; see `VERSIONING.md` |
| Push blocked by OPE gate during release prep | contract files changed without VERSION bump | bump `open-prompt-edition/VERSION` in the same push |

## Versioning

`swift/Sources/Phantom/Version.swift` is the single source of truth;
`build-app.sh` reads it into Info.plist; `release.sh` refuses to tag unless
it and `open-prompt-edition/VERSION` match the requested release.

`CFBundleVersion` (the build number) defaults to the repo's commit count
(`git rev-list --count HEAD`), so two builds of one commit agree and the
number only grows. `BUILD_NUMBER=<n>` overrides it — needed ONLY for tests
like the live-update decoy below. Sparkle compares `CFBundleVersion`, not the
marketing version, and refuses downgrades, which is why releases build only
from the private working repo: the squashed public repo has a commit count
of 1 and a DMG built there would be permanently uninstallable for existing
users (`publish-release.sh` enforces this with an exact-match origin guard).

## Sparkle update channel

No domain: the appcast and DMG live on the PUBLIC repo's GitHub Releases.
`SUFeedURL` is `releases/latest/download/appcast.xml`, so publishing a
release IS shipping the update. `publish-release.sh` signs the appcast with
the EdDSA key (private half: login Keychain only, never in the repo) and
fails closed on an unstapled DMG. Updates are consent-gated
(`SUAutomaticallyUpdate = 0`): the user sees the alert and clicks Install.

**Prove a real update installs before anyone else has the DMG** (an untested
updater is worse than none). The decoy recipe, proven 2026-09-05 for 1.0.0:

1. Edit `Version.swift` to a LOWER marketing version in the working tree only.
2. `BUILD_NUMBER=<less than the published sparkle:version> ./scripts/build-app.sh`
   — with `release.conf` present it is Developer-ID signed with the same
   `SUFeedURL` / `SUPublicEDKey`. Then `git checkout -- swift/Sources/Phantom/Version.swift`.
3. Quit the installed app; `pgrep phantom-api` must be empty (orphan check).
   `ditto build/Phantom.app /Applications/Phantom.app`;
   `defaults delete <bundle-id> SULastCheckTime`; `open` it.
4. Bring the app frontmost (see the failure table: the background alert is
   deferred while it is not). Install → Install and Relaunch.
5. Verify: Info.plist reads the published version/build,
   `codesign --verify --deep --strict` passes, `spctl -a -vv` says
   `Notarized Developer ID`, and the `MacOS/Phantom` binary's SHA-256 equals
   the one inside the release DMG. No `Autoupdate`/`Updater` processes left.
6. `rm -rf build/Phantom.app` — `build-dmg.sh dmg` reuses the last .app and
   would happily package the decoy.

Sparkle's release build writes nothing to the unified log; the evidence is
`SULastCheckTime` and `~/Library/Caches/<bundle-id>/org.sparkle-project.Sparkle/`.
